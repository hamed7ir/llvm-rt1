WHAT THIS IS
------------

rt1 is a small BINARY OVERLAY onto the official LLVM 18.1.8 win64 package. It is
NOT a fork, not a distribution, and not a replacement.

What is in this package (268 files):

  bin/                9 driver executables, rebuilt -- these are the modified
                      files this notice is about; plus 8 Microsoft VC runtime
                      DLLs, which are NOT ours and NOT modified -- see THE VC
                      RUNTIME below, and read it before you install
  lib/clang/18/include/   233 resource headers, matching the rebuilt clang
  patches/            the 10 patches, as readable diffs
  runtime/            4 files: aeabi-shim.c and a prebuilt aeabi-shim.lib /
                      aeabi-shim.obj for ARM32, plus README-aeabi-shim.txt
                      saying exactly when they are needed. These are the only
                      ARM32 TARGET binaries in the package; everything else

                      you -- see the README before adding them
  RELEASE-NOTES.md   the release notes: known differences, known
                      limitations, the porting checklist, provenance
  DISPOSITION-TABLE.md   every defect examined during this work, with one
                      verdict each -- the notes cite it by row (e.g.
                      "disposition table: D38a") and it ships so those
                      citations resolve for someone holding only this package
  LICENSE.TXT, MODIFICATIONS.txt

THE VC RUNTIME, AND WHY THIS PACKAGE SHIPS EIGHT MICROSOFT DLLs
---------------------------------------------------------------

Read this if you wonder why a compiler overlay carries msvcp140.dll.

The official LLVM 18.1.8 win64 package bundles its own copy of the MSVC C++
runtime in bin/, at version 14.29.30139 (the VS2019 16.11 toolset). These
drivers are built with the VS2022 14.44 toolset and import MSVCP140.dll.
Windows resolves an executable's own directory BEFORE the system directory,
so a driver copied into that bin/ loads the 14.29 runtime sitting beside it
instead of the newer system one -- and dies immediately with an access
violation (0xC0000005), printing NOTHING AT ALL. A consumer following the
install instructions would get a compiler that crashes on --version with no
diagnostic to go on.

So this package ships the 14.44 redistributable and replaces those eight
files one for one. MEASURED both directions before shipping: these drivers
work beside 14.44, and stock LLVM's OWN clang-cl still works beside 14.44
too -- the MSVC runtime is forward compatible within 14.x, which is the
whole reason this fix is safe rather than a trade.

  concrt140.dll   msvcp140.dll     msvcp140_1.dll             msvcp140_2.dll
  vcruntime140.dll  vcruntime140_1.dll  msvcp140_atomic_wait.dll
  msvcp140_codecvt_ids.dll

These eight are MICROSOFT's redistributable files, supplied under the Visual
Studio redistribution terms. They are NOT covered by the Apache-2.0 licence
in LICENSE.TXT, they are not modified, and no copyright in them is claimed
here. The official LLVM package ships the same eight for the same reason.

If you would rather not take Microsoft binaries from us, the alternative is
to DELETE all eight from bin/ after installing, so every tool resolves the
system copy instead. That works and is tested. It is not the default because
a consumer who forgets the step gets the silent crash described above.

⚠ rt1 1.0 AND rt1.1 SHIP WITHOUT THIS FIX and have the same defect: their
documented install produces a crashing clang-cl on any machine whose system
VC runtime is newer than the bundled 14.29. Neither was ever caught in house
because all in-house testing ran the drivers from the build tree, which has
no DLLs beside them. If you are using either, delete the eight files listed
above from your installed bin/, or move to rt1.2.


WHAT ELSE IS TOUCHED
--------------------

Apart from those eight runtime files, nothing else in an LLVM installation is
touched. NOTE the resource headers are
NOT byte-identical to the stock 18.1.8 set: they are what this clang was built
with. 225 of the 233 use CRLF line endings; the eight TableGen-generated ARM
headers (arm_neon.h, arm_mve.h, arm_sve.h, arm_sme.h, arm_cde.h, arm_fp16.h,
arm_bf16.h, arm_vector_types.h) are LF. The sanitizer/xray/profile/fuzzer/orc
headers are absent because those runtimes are not built here.

  Upstream base : llvmorg-18.1.8, commit 3b5b5c1ec4a3095ab096dd780e84d7ab81f3d7ff
  rt1.2 build   : commit 83c117cad0a9dee89e6daf6821c49156a3c562c0
                  (= the base plus the ten patches in patches/)

  rt1.2 is a THIRD FROZEN RELEASE, not an update stream. rt1's promise of no
  rebases and no version bumps still holds for rt1, for rt1.1 and for rt1.2.

Every binary here carries its provenance, but HOW YOU CHECK DEPENDS ON WHICH:

  the 4 clang drivers  --version prints "18.1.8-rt1" and the exact commit.
  the 5 lld drivers    --version never shows the commit -- lld strips the
                       version suffix. lld-link, ld64.lld and wasm-ld print
                       exactly "Varan LLD 18.1.8"; ld.lld prints "Varan LLD
                       18.1.8 (compatible with GNU linkers)"; and lld.exe
                       --version prints NOTHING and returns rc=1 with a usage
                       line on stderr, because lld.exe is a multiplexer, not
                       a linker driver.

The commit IS embedded in all nine. To verify an lld driver, search its bytes
for the commit string rather than trusting --version:

    findstr /M /C:"83c117cad0a9dee89e6daf6821c49156a3c562c0" <binary>     (cmd.exe)
    grep -ac 83c117cad0a9dee89e6daf6821c49156a3c562c0 <binary>           (git-bash/WSL)

AND CHECK THE OTHER HALF. rt1.1's and rt1 1.0's commits must both be ABSENT:

    findstr /M /C:"60876c5f8fad221756afd9bbd534377b7ff06571" <binary>     -> no match
    grep -ac 60876c5f8fad221756afd9bbd534377b7ff06571 <binary>           -> 0
    findstr /M /C:"7653a13d8d28189c7cef1401b934ec30d98ea353" <binary>     -> no match
    grep -ac 7653a13d8d28189c7cef1401b934ec30d98ea353 <binary>           -> 0

That second check is not decoration. The first rt1.1 build carried rt1 1.0's
commit by mistake, so the presence test alone PASSED on it and reported it as
the earlier release -- wrong, in the direction that matters. Presence without
absence cannot tell the releases apart.

WHAT A PASS LOOKS LIKE, and the two commands say it differently:

  findstr   prints the FILENAME and exits 0.  No output and exit 1 means the
            string is absent.  Note the -M: without it findstr tries to print
            the matching "line" of a binary.  A mistyped path also exits 1,
            with "FINDSTR: Cannot open ..." on stderr -- so read the message,
            not just the code.
  grep -ac  prints a NONZERO count (2 on every binary in this release, because
            the commit is stored twice) and exits 0.  A count of 0 with exit 1
            means the string is absent.

On all nine binaries of this package, findstr prints the filename and exits 0
for each, and grep -ac prints 2 for each -- 9 of 9 pass both, and 9 of 9 also
return 0 for rt1.1's and rt1 1.0's commits (measured 2026-09-14 by this project's
packaging harness, which lives in its private working repository and is not shipped).
Both commands were also run against the stock LLVM 18.1.8
clang.exe as a control and both correctly REJECT it (findstr exit 1 with no
output; grep -ac 0, exit 1), so neither command passes everything it is
handed.

A binary that contains neither that string nor the matching --version output is
not from this release.


WHAT WAS CHANGED
----------------

Ten patches, all included as readable diffs in patches/. Eight are ours; two
are backports of upstream's own fixes to a branch that never received them.

(rt1.1's copy of this file said "Eight patches" and listed only 0001-0008 while
shipping nine -- 0009 was never added to the list below. Corrected here.)

  0001  ARM: prologue over-allocated the frame by 8 bytes under the split
        R11/LR push, so SP- and base-pointer-relative frame references landed
        8 bytes below their assigned slots.                          [ours]
  0002  lld/COFF: a locally defined dllimport function got its __imp_ pointer
        written with bit 0 clear, so an indirect call through the slot
        requested ARM state on a Thumb-only device.                  [ours]
  0003  ARM: registers forwarded through a musttail call were not modelled as
        live, so a vcall thunk could use an argument register as scratch. [ours]
  0004  MC/CodeView: a tuple-register DBG_VALUE aborted the backend with
        "unknown codeview register".                                 [ours]
  0005  Tests for the this-adjusting thunk cases in 0003.            [ours]
  0006  clang: -Wpadded / -Wpadded-bitfield never fired under the Microsoft
        record layout builder.               [PORT of upstream's LLVM 21 fix]
  0007  ARM: a musttail vararg forwarder that also calls va_start aborted the
        backend.                                                     [ours]
  0008  clang: -fdump-record-layouts-complete crashed on records that cannot
        be laid out.        [PORT, verbatim, of upstream e4882d83d77f, LLVM 19]
  0009  ARM: Windows SEH (__try / __except / __finally) was rejected by the
        front end and unimplemented in the backend.                  [ours]
  0010  clang: _setjmp on Windows ARM32 was handed the frame pointer instead
        of the entry stack pointer, so longjmp died STATUS_BAD_STACK. [ours]

Patches 0006 and 0008 carry upstream's own fixes back to 18.x; no claim of
authorship is made over the upstream code or over the upstream tests shipped
with it. Patch 0008 additionally carries two rt1-authored tests
(dump-complete-invalid-field.cpp, dump-complete-uninstantiable.cpp), because
upstream's invalid-base test does not fault on 18.1.8 and so does not arm the
guard's second half.

Series footprint against the upstream base (llvmorg-18.1.8,
3b5b5c1ec4a3095ab096dd780e84d7ab81f3d7ff): the ten patches touch 40 files,
+2,333 / -127. Twenty-six of those files are modified (+547/-127); fourteen
are new test files (+1,786/-0). Counted with `git apply --numstat` over unique
paths -- the same method reproduces rt1 1.0's published 22 files / +1,239 / -32
for its eight patches, so the two releases' figures are comparable.


WHAT WAS NOT CHANGED
--------------------

No layout, ABI or calling-convention behaviour was altered to "fix" a difference
from MSVC. Where clang-cl and MSVC disagree, this release DOCUMENTS the
difference. The layout scanners are published in the rt1 source repository
alongside the release notes; they are not part of this binary overlay -- what
ships here is patch 0006's -Wpadded / -Wpadded-bitfield diagnostics, inside
clang itself. Changing layout would desync these binaries from the MSVC 14.16
CRT and from every MSVC-built library in a consumer's link, which is worse
than the difference itself.

SOURCE
------

The complete corresponding source is reproducible from the public upstream tag
plus the patches in this package:

    git clone https://github.com/llvm/llvm-project.git
    cd llvm-project && git checkout 3b5b5c1ec4a3095ab096dd780e84d7ab81f3d7ff
    git apply /path/to/patches/000*.patch

Or, without a full clone -- the tarball at the tag is a few hundred MB against
several GB of history, and rt1's own clone attempts failed twice on this link:

    curl -LO https://github.com/llvm/llvm-project/archive/refs/tags/llvmorg-18.1.8.tar.gz
    tar xf llvmorg-18.1.8.tar.gz
    cd llvm-project-llvmorg-18.1.8
    patch -p1 -F0 < /path/to/patches/0001-....patch      (repeat, in order)

TWO NOTES IF YOU TAKE THE TARBALL ROUTE, both learned here:

  * Use `patch`, not `git apply`, on an extracted tarball. An extracted tree
    has no .git, so git walks UP looking for one; if it finds an enclosing
    repository, and the extracted path is ignored by that repository, `git
    apply` SKIPS every file and still exits 0. It reports success and changes
    nothing (measured here).

  * CMake stamps the version string from whatever repository it finds by the
    same upward walk, so a tarball build can embed a commit from an unrelated
    repo.  Pass -DLLVM_FORCE_VC_REVISION=3b5b5c1ec4a3095ab096dd780e84d7ab81f3d7ff
    if you want the version string to be right, or -DLLVM_APPEND_VC_REV=OFF if
    you would rather it say nothing than say something false.

Build configuration: the literal configure command line used for this
release (substitute your own checkout/build/ninja paths for the
placeholders below; the -D flags are the actual configuration):

    cmake -S <llvm-project-checkout>/llvm -B <build-dir> -G Ninja ^
      -DCMAKE_MAKE_PROGRAM="<path-to-ninja.exe>" ^
      -DCMAKE_BUILD_TYPE=Release ^
      -DLLVM_ENABLE_PROJECTS="clang;lld" ^
      -DLLVM_TARGETS_TO_BUILD="ARM;X86" ^
      -DLLVM_VERSION_SUFFIX="-rt1" ^
      -DCLANG_VENDOR="Varan" ^
      -DLLD_VENDOR="Varan" ^
      -DLLVM_PARALLEL_LINK_JOBS=2 ^
      -DLLVM_ENABLE_ASSERTIONS=OFF ^
      -DLLVM_INSTALL_UTILS=ON ^
      -DLLVM_INCLUDE_BENCHMARKS=OFF ^
      -DLLVM_INCLUDE_EXAMPLES=OFF ^
      -DLLVM_INCLUDE_DOCS=OFF ^
      -DLLVM_ENABLE_ZLIB=OFF ^
      -DLLVM_ENABLE_ZSTD=OFF ^
      -DLLVM_ENABLE_LIBXML2=OFF ^
      -DLLVM_ENABLE_PDB=OFF ^
      -DLLVM_ENABLE_DIA_SDK=OFF ^
      -DCMAKE_INSTALL_PREFIX=<install-dir>

Run this inside an MSVC vs22buildtools 14.44 vcvars64 environment, with
Ninja 1.13.2 as the generator's make program. Static linking (no LLVM DLLs;
BUILD_SHARED_LIBS=OFF) and the /MD runtime are this LLVM configuration's own
CMake defaults, not flags set explicitly above.

LLVM_ENABLE_DIA_SDK is DIFFERENT: it IS set explicitly above, and it has to
be. LLVM defaults that option to whether the host has the MSVC DIA SDK
(llvm/cmake/config-ix.cmake tests IS_DIRECTORY on MSVC_DIA_SDK_DIR). This
release's build host DOES have it, so the default here is ON. An explicit
-DLLVM_ENABLE_DIA_SDK=OFF is required to reproduce these binaries from an
empty build directory. "No ATL" follows from OFF however OFF is reached. It
is not evidence about the host. A missing DIA SDK would not imply a missing
ATL in any case -- they are separate VS components.
build-rt1.bat and cmake-rt1.bat are vcvars64 wrappers that live in the rt1
SOURCE repository, not in this binary overlay: they set the MSVC host
toolset environment (vcvars64 + INCLUDE) and forward their arguments to
ninja / cmake.exe. They carry none of the configuration above themselves,
and this package does not include them.
